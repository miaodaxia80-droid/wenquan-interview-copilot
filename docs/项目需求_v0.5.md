## 1. 产品主张

**问全面向有准备、有主线的访谈主持人。** 主持人在访谈前设置本次主题、希望聊出的内容和主线顺序；访谈中，问全持续转写对话，对照主线整理已经获得的信息，再给出几个适合当前语境的可选问题。主持人决定问什么、何时问。随着问题被提出、嘉宾继续回答，问全更新信息状态与建议，直到主持人结束本次访谈。

这里的主持人包括人物访谈、播客、视频访谈和专题对谈的主持者。首个重点场景为一位主持人与一位嘉宾、具有明确主题和若干主线的中文访谈。多人圆桌和复杂现场调度留待后续验证。

一句话介绍：

> **问全是主持人的实时访谈助手：沿着你设定的主线，跟随嘉宾的回答，持续提供下一步可选提问。**

产品演示围绕一场访谈展开：会前确定主线，现场听到新的信息，建议问题随回答变化，最后按主线回看聊到了什么、哪些问题仍未展开。FDE 和用户研究材料保留为历史测试场景，当前主叙事转为主持人访谈。

## 2. 核心使用需求

主持人往往已经有一份提纲，现场需要同时理解嘉宾的回答、判断值得深入的内容、维持主线推进并自然衔接下一个话题。需要验证的需求包括：

- 嘉宾提到意外经历或关键选择时，及时抓住可以深入的线索。
- 判断某段主线已经获得哪些信息，还有什么值得补问。
- 嘉宾提前回答了后面的提纲问题时，减少重复提问。
- 话题展开较远时，找到自然回到主线的方式。
- 主持人提出问题后，跟踪嘉宾是否回应，而非只记录“问过了”。

这些是设计假设，尚不能据此宣称已改善访谈质量或获得主持人的持续使用意愿。

## 3. 产品循环

**设定访谈内容与主线 → 实时转写 → 整理新信息 → 更新主线状态 → 提供候选问题 → 主持人提问 → 等待并理解回答 → 更新候选 → 结束访谈。**

系统持续处理信息，主持人掌握现场节奏。候选问题是可选建议，允许忽略、改写、稍后再问，也允许在没有合适建议时保持空白。

“主线”是本次访谈希望展开的若干内容，顺序可调。例如“转行的起因 → 最难的一次决定 → 实际变化 → 对后来者的建议”。每条主线可包含主持人预先准备的问题、想获取的信息与优先级。它不要求所有访谈都套用统一的检查表。

## 4. 会前准备

主持人在手机端填写：

| 信息 | 内容 | 是否必需 |
|---|---|---|
| 访谈主题 | 本次访谈围绕什么展开 | 必需 |
| 访谈目标 | 希望通过这次谈话让听众理解什么 | 必需 |
| 嘉宾背景 | 身份、与本主题有关的已知经历；注明资料来源 | 可选 |
| 访谈主线 | 若干有顺序、可调整的章节，每章说明想聊什么 | 至少一条 |
| 预设问题 | 主持人已经准备的问题，可归入对应主线 | 可选 |
| 重点与边界 | 必聊内容、希望深入的方向、不希望展开的内容 | 可选 |

主线由主持人编写，也可以由模型根据主题和目标提出草案，再由主持人确认、删除或调整。模型生成的背景和提纲不能自动成为已知事实。

下一版优先支持直接填写、编辑和调整主线顺序。文档文件导入属于后续功能，不把尚未实现的导入能力放入首版演示。

准备页确认后开始前台连续采集。保持明显的录音状态，主持人可暂停、停止或结束。当前服务与设备限制沿用既有实现，详见运行说明。

## 5. 会中分析与主线状态

系统用稳定转写更新信息，中间识别文字仅用于预览。每次分析结合当前主线、相关历史、已问问题及最新回答，提取嘉宾具体说过的经历、观点、理由和未展开之处。

访谈内容应区分主持人的问题与嘉宾的回答。主持人的问句、问题中的假设和未被嘉宾确认的表述，均不能直接记为嘉宾观点。嘉宾说出的主张也只是有出处的口头陈述，不能自动视为已经核实的事实。

主线状态与问题状态分别管理：

| 对象 | 状态与含义 |
|---|---|
| 主线章节 | 未展开、正在展开、已有内容、待补充、主持人确认结束 |
| 建议问题 | 候选、当前展示、已问待回应、已回应、稍后、跳过、被新信息替代 |

“已有内容”表示该章已有相关信息，不代表访谈深度足够。“已问”表示主持人提出了问题，不代表嘉宾回答了问题。“已回应”也不等于内容完整，仍可以根据回答继续深挖。

模型可以建议当前涉及哪条主线、是否值得继续或转场；主持人可手动定位当前章节，调整后续顺序。模型建议不自动把章节判定为结束，也不以信息条数强制切换话题。

## 6. 候选问题与刷新规则

### 6.1 少量、有区别的候选

初版目标为同时提供 **0–3 个候选问题**；有价值的问题不足三个时少给。候选根据现场内容选择，不要求每次凑齐以下类型：

| 类型 | 何时有用 | 问题依据 |
|---|---|---|
| 顺着回答深挖 | 嘉宾提到一个值得展开的经历、选择或观点 | 明确对应某段原话 |
| 补充当前主线 | 已聊到主题，但尚缺相关背景、经过、理由或具体例子 | 主持人的主线要求与已获得的信息 |
| 过渡到下一主线 | 当前话题已展开，主持人可以顺势推进 | 已确认的提纲和当前上下文 |

每个候选简短说明“为什么此时可以问”，标明所属主线。深挖题保留可定位的原话；主线补问题和过渡题可以来自提纲，明确标为提纲依据，不强行制造嘉宾引用。所有建议都应避免重复已获回答、在问题中捏造嘉宾经历或暗示未经证实的结论。

候选之间应有不同的信息目标。三个措辞相似的问题不算三个有效选择。建议保持自然口语，一次聚焦一个主要问题，主持人可自行改写。

### 6.2 主持人提问后的循环

1. 主持人选择一个候选，或按自己的判断提出其他问题。
2. 识别到主持人提出问题，或主持人标记“已问”后，将相应问题置为“已问待回应”。其他候选仍可保留。
3. 嘉宾回答期间继续转写，等待稳定内容再判断，不因主持人的问句就把主线标成已经回答。
4. 收到新信息后，补充主线记录，撤下已被回答的候选；根据仍值得展开的内容重新提供候选。
5. 若回答偏离问题或暂未回答，记录待补充，允许继续追问或暂时保留。
6. 重复上述过程，直到主持人主动结束访谈。

“已问”的手动标记可作为首版可靠入口，但自动理解主持人与嘉宾轮次仍是目标体验的一部分，不能用手动按钮宣称已经实现自动识别。主持人自己提出的问题也应进入问题历史，避免建议重复。

### 6.3 稳定展示

- 以稳定分句和有意义的新信息触发分析，不随 ASR 每个中间字刷新整组候选。
- 流式生成时展示生成进度与临时草稿，校验完成后才替换正式候选。
- 新结果不应无条件打断主持人正在阅读的问题。保留当前展示项；新候选到达时提示可查看。
- 已获得回答的问题应及时撤下；旧请求晚到、切换主线或更正转写后，过期结果不能覆盖新状态。
- 主持人可选择“稍后”或“跳过”；没有新依据时不反复推回同一个问题。
- 暂停后停止采集和主动更新；结束后不再发送现场提示。

刷新频率、候选数量和保留当前展示项的细节需要实机试用确定，不把本版默认建议写成已经验证的最佳交互。

## 7. 手机与眼镜分工

手机准备页承载主题、目标、嘉宾背景、主线和预设问题。访谈页展示当前主线、最多三个候选、正在回应的问题、实时转写及简要信息记录。主持人可以切换主线、选候选、标记已问、稍后或跳过。

眼镜优先保证现场可读性：**一次展示一个候选问题，并提示还有其他候选可选**。下一轮先复用手机选择并同步到眼镜的路径；通过眼镜按键切换候选，须依据公开 SDK 和真机验证后接入。现有 0.2.5 未实现多候选切换。

不在眼镜上堆叠三段长问题或整份提纲。当前一题展示和多个候选属于不同层次：主持人有选择，眼镜展示保持简短。这个方案仍需用佩戴体验检查阅读负担与操作成本。

## 8. 主持人与嘉宾的区分

本场景需要区分主持人的问句与嘉宾回答。自动检测“主持人已经问了什么”依赖可靠的说话人归属，仅检测问号或疑问语气不足以成立，因为嘉宾也会反问或转述他人的提问。

建议分阶段实现：

1. 先保留明确的手动“已问”和角色更正入口；转写归属不明确时标记未知，不自动写成嘉宾事实。
2. 接入 ASR 说话人编号，通过主持人确认将编号绑定到主持人或嘉宾；音色编号与真实身份分开保存。
3. 结合轮次、文本和候选问题历史判断主持人实际问了什么，对不确定的识别保留更正入口。

当前已做过合成音频的 ASR 说话人编号可行性测试，但 **0.2.5 尚未接入编号与访谈角色的映射，也没有完成自动“已问”识别**。真实环境中的重叠发言、编号变化和误识别仍需验证。本版不宣称可凭音色直接知道真实姓名或社会角色。

## 9. 会后结果

主持人结束访谈后，按主线回看：本章获得了哪些内容、对应嘉宾原话、实际问过的问题、仍未展开的问题，以及访谈中出现的新线索。原始转写保留，允许更正与导出。

首版优先形成可编辑的主线摘要和问题记录。文章、播客简介和视频剪辑点可以作为后续功能，不纳入本轮核心闭环，也不把嘉宾陈述自动包装为已经核实的新闻事实。

## 10. 一场访谈的演示主线

以下内容为虚构设计脚本，用于下一轮验证；尚未作为模型实测结果。

**访谈主题：一个普通人第一次做独立项目的经历。** 目标是聊清楚为什么开始、关键决定、踩过的坑以及现在的看法。主线设为“起因 → 关键选择 → 最大困难 → 回看与建议”。

| 时刻 | 现场内容 | 问全应如何变化 |
|---|---|---|
| 会前 | 主持人确认四条主线与预设问题 | 保存准备内容，保留主持人的顺序 |
| 嘉宾开场 | “当时工作挺稳定的，但我总想试试自己的东西。” | 记为嘉宾自述；可建议“是什么具体经历让你决定真的开始？”或“你说的‘自己的东西’，当时有明确想法吗？” |
| 主持人深挖 | “是什么具体经历让你决定真的开始？” | 标记已问待回应，等待嘉宾回答 |
| 嘉宾补充 | “朋友请我帮忙做个小工具，做完以后，有几个陌生人也愿意用。” | 补充起因，撤下已回答的起因题；可建议“看到陌生人开始用，你做的第一个决定是什么？” |
| 出现新线索 | “后来我决定先不辞职，下班后继续做。” | 围绕关键选择，候选可以是“当时为什么决定先保留工作？”与“你怎么安排工作和项目的时间？” |
| 主持人推进 | 主持人选择聊最大的困难 | 切换当前主线，保留尚未采用的有价值线索，避免强行拉回旧话题 |
| 结束 | 主持人点击结束访谈 | 停止采集和提示，按四条主线整理内容与尚未展开的问题 |

演示重点是同一场访谈里的连续变化：新回答带来了什么信息、为什么原来的建议退出、下一个候选如何衔接主线。不能以固定脚本展示代替模型实时理解的验证。

## 12. 实施顺序与技术边界

### 第一轮：主线与候选闭环

- 增加主持人访谈模板，以主题、目标、主线和预设问题为准备入口；保留旧主题和历史记录。
- 模型接口从单条 `question` 演进到有上限的候选集合，为主线 ID、问题类型、依据类型、候选状态和当前展示项建立独立字段。
- 区分转写证据与提纲依据。现有接口要求问题引用当前片段，直接把它用于转场题会造成引用不符或编造，必须同步修改前后端校验与流式预览。
- 实现 0–3 个候选、逐个已问/稍后/跳过、回答后去重与更新；当前阅读项与新候选分开处理。
- 先以标注了主持人和嘉宾的合成转写验证逻辑，再验证真实说话人链路；演示时说明输入来源。

### 第二轮：现场自然轮次

- 接入说话人编号、主持人/嘉宾绑定与归属更正。
- 识别主持人实际问题，包括未采用候选的自拟问题，并关联后续回应。
- 按主线维护有来源的累积信息，测试长访谈中早期内容、主题提前回答和回到旧主线的情况。
- 完成实体手机、实际佩戴眼镜和一场完整主持人访谈的验证，再确认刷新节奏和候选数量。

现有单题 JSON 客户端与新接口需要兼容或显式版本化。不能直接改变已安装 0.2.5 所依赖的响应结构后宣称旧端仍可正常工作。模型输出仍须检查结构、依据、主线归属和状态版本；流式草稿不自动写入正式访谈记录。

## 13. 验收重点

| 场景 | 通过条件 |
|---|---|
| 准备与主线 | 主持人可编辑主线与顺序，现场可定位当前主线 |
| 多候选 | 同时 0–3 条，各有不同信息目标、所属主线和可解释依据 |
| 连续问答 | 主持人提问后等待回应，新回答确实改变信息和候选 |
| 提前回答 | 嘉宾提前回答后续章节内容时，被记录到对应主线，减少重复建议 |
| 主持人自拟问题 | 不必选中候选也能进入已问历史，并影响后续建议 |
| 角色与事实 | 主持人的假设、嘉宾的反问不被当成已经确认的嘉宾观点 |
| 依据类型 | 深挖题引用有效原话；提纲题明确来自主线，不冒充嘉宾说过 |
| 稳定阅读 | 新结果到达不无条件顶掉正在阅读的问题；已回答题及时撤下 |
| 结束与恢复 | 暂停或结束停止更新；错误、断网与晚到结果不破坏记录 |
| 实际佩戴 | 主持人能读懂、选择或忽略建议，记录实际交互成本与干扰 |
